## 1. AI & Software Engineering (L1)

**Two connections between SE and ML**
| Direction | Meaning |
|---|---|
| **AI4SE** (AI for SE) | Use AI to help build software |
| **SE4AI** (SE for AI) | Engineer systems that contain AI components |

**SE vs ML**
| SE | ML |
|---|---|
| Structured / process-oriented (Agile, Waterfall) | Experimental, empirical |
| Correctness vs spec | Accuracy (statistical) |
| Code-focused | Data-focused, algorithm-focused |

**ML tradeoffs:** accuracy, capabilities, training data needed, inference latency, learning latency, model size, explainability.

**AI across the SDLC** (AI = *force-multiplier*, not a replacement)
| Phase | With AI | Human still needed for |
|---|---|---|
| Project mgmt | Forecast timelines, resources, budget (MS Project, Asana Intelligence) | Decisions |
| Requirements | Chatbot elicitation, draft specs from user stories, gap analysis | Validate with stakeholders, resolve conflicts, scope |
| Architecture | Pattern recommendation, diagram generation, risk analysis | Trade-offs (perf vs maintainability, monolith vs microservices), peer review |
| Coding | Copilot autocomplete, code review automation | Understand code, business logic, security |
| Testing | Test generation, AI fuzzers, coverage analysis | Acceptance criteria, false pos/neg, business-critical cases |
| Deploy/DevOps | Pipeline optimisation, anomaly detection, rollback support | SLOs, rollback policies, "you broke it, you fix it" |
| Maintenance | Bug triage, tech-debt prediction, refactor suggestions | Road-mapping, prioritisation |

### Worked examples from slides (College Event Mgmt App)

**Requirements draft** (browse events, register, create/edit events, cancel registration, notifications).
- *Missing:* authentication/roles & login; event capacity/waitlist; payments; search/filter; admin; non-functional reqs (performance, security).
- *Incomplete:* "Notifications will be sent" – no channel (email/SMS/push), timing, or recipients.
- *Why AI missed:* only had a short summary, no stakeholder context. *If uncaught:* costly rework later.

**Architecture** (single monolithic server). Issues: single point of failure, hard to scale, tight coupling, notification load slows registration, no caching/redundancy. Fixes: separate notification service/queue, load balancer, replicate DB, consider modular monolith or microservices.

**Code – find the vulnerability**
```c
void process_event_name(char *input) {
  char event_name[50];
  strcpy(event_name, input);   // BUFFER OVERFLOW – no length check
  printf("Processing event: %s\n", event_name);
}
```
Fix: `strncpy`/`snprintf` with size, null-terminate, check input is non-NULL, validate length. (Also: `printf("%s")` is fine; `printf(input)` would be a format-string bug.)

**AI-generated tests** (valid, empty name, empty user, 500-char name). Gaps: NULL input, special chars/injection, duplicate registration, capacity full, boundary (exactly 50 chars / 49 / 51), concurrency, unicode.

### AI code limitations (stats to remember)
- ~**40–45%** of AI snippets have security flaws; **1689** Copilot programs studied → **40%** exploitable.
- Insecure rates: **XSS 86%**, **Log injection 88%**, **SQL injection 20%**, **crypto 14%**.
- *Why:* trained on vulnerable public code; limited semantic understanding; no app-specific knowledge (roles, threat model); may leak keys.
- **Risk: overreliance** → reduced critical thinking.

### When should an LLM solve it? (decision framework)
1. **Alternatives** – deterministic solution better? (Type-checking Java → **No**, use compiler)
2. **Error probability** – how often is it right? (Grading proofs → risky)
3. **Risk tolerance** – cost of a mistake? (Emergency medical → **No**)
4. **Risk mitigation** – can outputs be verified? (Unit test generation → **Yes**, tests can be run/reviewed)

**Key takeaways:** SDLC still governs; human oversight non-negotiable; new skills (prompting, critical review), same fundamentals.

## 2. SE for ML Systems (L2)

- **ML model ≠ ML system.** Model is one component; real systems have many ML + non-ML parts (only a fraction is ML code – Sculley "Hidden technical debt").
- **ML model = unreliable function:** may make mistakes, confidence unreliable, opaque, judged by *accuracy not correctness*.
- **Lack of specification** → breaks modular reasoning, QA, safety/fairness reasoning, team coordination. (`sum()` has a spec; `detectObjects(image)` does not.)
- Test expectation shift: not "100% pass rate" – e.g. 63 failures can be OK.

**Typical ML pipeline**
- *Static:* data collection/cleaning/labeling → feature engineering → train/eval split → train → evaluate → repeat.
- *In production:* monitor → select data for retraining → update/deploy model regularly.

**MLOps** = specialised subset of DevOps for ML (training, evaluation, versioning, deployment automation). *But there's more to ML systems than MLOps.*

**Planning for mistakes (Smart Toaster example)**
| Inside model | Outside model (safer) |
|---|---|
| Max toast time, heat sensor prediction – hard to guarantee | Code check for max time; non-ML shutdown if too hot; **thermal fuse** (hardware) |

**Fault-tolerant strategies:** human in the loop · undoable actions · mistake detection & recovery (monitoring, doer-checker, fail-over, redundancy) · **guardrails** · containment/isolation. *Never rely solely on the model.*

**Hazard analysis:** worst thing that can happen? Backup strategy? Undoable? Non-technical compensation?

**Architecture decisions for ML:** components & responsibilities · monolith vs microservices · sync vs async · APIs & access · **where inference runs (client vs server)** · telemetry storage · DB centralised vs decentralised.

**Quality requirements drive architecture:** cost, time-to-release; scalability, availability, response time, throughput; security, safety, usability, fairness; modifiability; ML-specific: accuracy, data collection, training latency.

**Where should the model live? – considerations:** input data size, output size, execution speed/energy, latency needed, model size & update frequency, operating cost, offline behaviour.

### How to solve the AR Smart Glasses activity (Object Detection / Motion Tracking: Cloud vs Phone vs Glasses)
Make a table, score each qualities: latency, bandwidth, battery, offline, model size.
| Component | Suggested home | Reason |
|---|---|---|
| **Motion tracking** | **Glasses (on-device)** | Needs very low latency (any lag → motion sickness), small model, must work offline, uses sensor data locally |
| **Object detection** | **Phone** (or cloud for heavy models) | Heavy compute/model size, glasses have tiny battery; phone has more power with lower latency than cloud; cloud costs bandwidth for video upload and fails offline |

Template answer: *state choice → list 2–3 relevant qualities → state the trade-off you accept.*

## 3. Implementation & Coding Standards (L2-3)

**Implementation facts:** 40–50% of project effort; 1000s–10000s of config items; ~**80% of time reading existing code**. Input = design doc, output = executable software (input to testing).

**Before coding:** compiled vs interpreted language · dev environment · Configuration Management Plan.
**During coding:** coding standards/guidelines, language syntax, quality/security/testability, unit-tested + peer-reviewed code.
**Phase characteristics:** high volume of config items · heavy CS knowledge · tied to quality · tool-intensive.
**Cost of fixing bugs rises sharply the later it is found** → quality now.

### Choosing a language – checklist
Ecosystem/vendor support · environment (web/mobile) · infra/deployment · client preference · libraries/tools · developer availability/skills · constraints (time, budget) · performance · security.
Abstraction levels: Assembly → Procedural → Aspect-oriented → Object-oriented.

**Scenario answers**
- *Scenario 1 (real-time notifications, 5000+ concurrent users, existing Java portal, limited budget):* **Java** (or Kotlin) – integrates with Java portal, strong concurrency, uses existing infra. (Node.js is an alternative for async I/O, but integration cost is higher.)
- *Scenario 2 (analytics dashboard, stats + visualisation, non-technical users, 6-week prototype):* **Python** (pandas, matplotlib, Streamlit/Dash) – fast prototyping, rich stats libs.

### Characteristics of good code
1. **Simple & clear** – reasonable lines/function, functions/file, args/function, nesting levels, conditions.
2. **Naming conventions** – meaningful; avoid keyword-like names; don't start with `_` (except internal-use prefix style); 2–3 min / 30 max chars; no reused numeric values in names.
   | Style | Rule | Example | Used for |
   |---|---|---|---|
   | Pascal | First letter upper | `BackColor` | Class / variable names, method params |
   | Camel | First lower, rest words upper | `backColor` | Method names |
   | Underscore prefix | `_` + camel | `_backColor` | Internal class/method use |
3. **Structuring** – dependencies visible via naming/layout; logically grouped `#include`, `#define`, structs, functions; good header/C file split; encapsulated, initialised data.
4. **Readable** – whitespace is free, meaningful names reduce comments.

### Naming exercise – how to solve
Look for: misleading names, wrong case style, vague names (`temp`, `FLAG`), ALL_CAPS for non-constants.
```c
// BAD: 'uglyduck' & 'timer_count' mislead – it's a factorial
int factorial(int n) { if (n <= 1) return 1; else return n * factorial(n - 1); }

// BAD: process_str / INPUT_STR / FLAG / temp
char* transform_string(char* input_string, int should_transform) {
    char* transformed_string = malloc(strlen(input_string) + 1);
    if (should_transform) { /* some processing */ return transformed_string; }
    return input_string;
}
```
*(Bonus: the original also leaks the malloc'd buffer when the flag is false, since malloc happens before the check, and never checks malloc for NULL.)*

**Comment exercise tip:** one comment on the function's purpose + inline comments only where logic is non-obvious (e.g. why a null check). Note bugs in the sample: `getElementbyID` should be `getElementById`, and an id with a space (`"Code Comment"`) is bad.

### Good programming style
**Do:** few agreed control constructs · disciplined GOTO · user-defined types for domain entities · hide data behind access functions · good names · indentation/parentheses/blank lines.
**Don't:** be too clever · dangling if / dangling else · nest deeply · reuse an identifier for multiple purposes · routines with **> 5 formal parameters** (examine them).

### Dangling else – how to solve
```c
k=0; o=0;
if (ch >= 3)
  if (ch <= 10) k++;
  else o++;          // else pairs with the NEAREST if (ch <= 10)
```
Rule: **else binds to the closest unmatched if**, regardless of indentation.
| ch | result |
|---|---|
| 2 | nothing (outer if false; else NOT executed) |
| 5 | k++ |
| 11 | o++ |
Fix with braces: `if (ch>=3) { if (ch<=10) k++; } else o++;` (when you want the else on the outer).

### Coding standards
Uniform look, readability, maintainability, reuse, sound practice. Examples: data usage rules, standard module headers, naming, error/exception handling. Practices: **testable, secure, defensive programming**.

### Defensive programming (Murphy's Law) – the event registration code
Code: `register_for_event` opens file, counts registrations, appends if under capacity.

| Category | Problems |
|---|---|
| **5 failure scenarios** | Race condition/TOCTOU (2 users, 1 seat) · file doesn't exist yet · `strstr` substring collision ("Tech" matches "TechFest") · `line[100]` truncation · disk full / permission denied |
| **Missing checks** | `fopen` NULL check · NULL/empty args · delimiter injection (`,` `\n`) · duplicate registration · ignored `fprintf`/`fclose` return values |
| **Resource mgmt** | `fclose(NULL)` UB · file opened before knowing event is full · no file locking · O(N) scan per write |
| **Data integrity** | Interleaved writes · injected records (`"eve,HackCon\nadmin"`) · commas in names shift columns |

Mindset: *"Code like the user is actively trying to break your system."*

### Secure programming practices
Validate all untrusted input · heed compiler warnings (max level) · static + dynamic analysis · **default deny** · **least privilege** (for least time) · sanitise data sent to other systems.

## 4. Testable Programming, Agile Quality, Code Reviews, Archaeology (L4)

### Static analysis (intro)
Examines code **without running it**. Finds: programming errors, standard violations, undefined values, syntax violations, security vulnerabilities. Static = white-box; dynamic = black-box scanning of running app.

### Testable programming practices
| Term | Meaning |
|---|---|
| **Assertions** | Catch out-of-range values |
| **Test points** | Get/set module status & variables |
| **Scaffolding** | Code written only to support unit/integration testing |
| **Test harness** | Code that drives modules as part of the system |
| **Test stubs** | Return fixed known values to stand in for functions not under test |
| **Instrumenting** | Logging to visualise execution |
| **Test data sets** | Valid *and* invalid data |

**Coding guidelines** (vs standards): generic, improve readability, cut early-error cost, ease maintenance – document well, indent, short functions, minimal GOTO, no identifier reuse.

### Agile quality metrics
| Metric | Meaning |
|---|---|
| **Sprint burndown** | Work remaining (story points) vs time; slopes down to zero |
| **Velocity** | Story points (or hours) completed per sprint – used for planning |
| **Throughput** | Units of work completed per time period |
| **Cycle time** | Time from starting an item to finishing it |

*Quick calc:* if velocity = 30 pts/sprint and backlog = 120 pts → 120 / 30 = **4 sprints**.

### Construction technical quality
Peer review · unit testing · **test-first** (design tests before code → clarifies requirements, ensures testability) · code stepping · pair programming (one logic, one syntax) · debugging · **code inspection** (formal peer review) · static analysis.

### Code reviews
**Why when we already tested?** Reviews catch more defects, spread knowledge, and force better documentation.
- Detection rates: **unit test 25%, integration 45%, design inspection 55%, code inspection 60%**.
- 11 programs: no reviews **4.5 errors/100 LOC** → with reviews **0.82/100 LOC** (≈ 82% reduction: (4.5−0.82)/4.5 = 0.818).
- AT&T: **+14% productivity, −90% defects**.
- Company practices: Google (≥1 reviewer, readability in language), Yelp (review-board, "Ship It!"), Facebook (all versions retained, weekly push).
- **Holistic reviews** – goal/architecture/design; meeting-based. **Incremental reviews** – each change signed off by a *committer* before commit.

**Review checklist:** Design · Functionality · Complexity · Tests · Naming · Comments · Style · Documentation.

### How to review the `login_user` code
1. **Security:** hard-coded admin credentials (`admin`/`123`); plaintext password comparison (should hash + salt); no rate limiting / lockout; timing attacks.
2. **Functionality:** `get_users()` "assume this works" – no error handling; loads all users each login (inefficient, privacy risk); `return False` is mis-indented in the pasted code.
3. **Maintainability:** magic strings, no docstring, no tests, loop could be a DB query.
→ Verdict: **Do Not Ship**.

**Constructive review rules:** criticise code not coder · explain *why* · suggest improvements · pick battles · ask questions.
**Good pull request:** concise title, context/rationale/alternatives, links to issues/specs, screenshots for UI.

### Code archaeology (understanding a new codebase)
Goal: build a **working model** (components + connections) via observation, probes, hypothesis testing. *You will never understand the entire system.*

**Steps:** clone → README → folder structure → build → run → attach debugger → find logs → search constants (strings, colours, magic ints like `0xDEADBEEF`).
| Novice | Expert |
|---|---|
| Reads line by line, trial & error, only happy path | Top-down, pattern-recognition, hypotheses, checks up/downstream |

**Where does code live?** local binaries · local source (build+run) · server-side web app (remote, observe outputs only) · client-side JS (downloaded, use dev tools).
White-box (P+U+E: probe, understand, edit) > grey-box > black-box.

**Static gathering:** IDE, grep/find. **Dynamic gathering:** build → run → change → run → compare. **Probes:** print, structured logging, debuggers (breakpoint/step), delete debugging, Chrome DevTools. **Share findings:** README, wiki, Mermaid diagrams, include negative results.

**Redis example (ZADD crash/memory):** `server.c` (main, command table) → `t_zset.c` (`zaddCommand`, skiplist + dict) → inspect arg parsing, malloc checks, NULL handling, cleanup on errors → run `make test`, build with debug flags, use **valgrind**.

## 5. Static Analysis Tools (L5)

**Can do:** type checking (well-established), syntax-pattern checks (e.g. `==` on Java strings, `a[i]` without bounds check).
**Cannot:** reason about termination (Halting problem); exact values are hard → **conservative abstraction**, so expect **"MAYBE"** answers and over-approximation (false positives).

**Good at detecting:** security (buffer overruns, unvalidated input) · memory safety (null deref, uninitialised data) · resource leaks.
**Also:** find bugs, refactor, style, code smells, quality measure, accessibility, performance bottlenecks.

**What makes a good tool:** fast · **few false positives** · continuous (in CI, diff-based) · informative (suggest/apply fixes).

**Classification**
| Type | Notes |
|---|---|
| **Linters** | Shallow syntax; style, indentation, naming, line size. Cheap, fast |
| **Pattern-based bug detectors** | Bad practice, correctness, performance, security, dodgy code, multithreading… (e.g. SpotBugs) |
| **Type-annotation validators** | `@Nullable`/`@NonNull` (Checker Framework), MyPy, TypeScript |
| **Data-flow / abstract interpretation** | Deep; "can index be out of bounds?" – costly |

**Type annotation limits:** only sees signatures; weak on dynamic code (Spring, templates); false positives; needs annotated libraries; hard to retrofit.
**Mars Climate Orbiter ($327M)** – Newtons vs pound-force mismatch (type/unit checking could have caught it).

**Static vs Dynamic analysis**
| | Static | Dynamic |
|---|---|---|
| Needs | Source only | Build + test inputs |
| Coverage | All paths/inputs (conservatively) | Only observed executions |
| Errors | **False positives** | **False negatives** |
| Reports | May be spurious | Real (witnessed) |

**Best QA = combine multiple tools.**

### How to solve the `n2s` activity (number → string in base b)
```python
def n2s(n: int, b: int):
    if n <= 0: return '0'
    r = ''
    while n > 0:
        u = n % b
        if u >= 10: u = chr(ord('A') + u - 10)
        n = n // b
        r = str(u) + r
    return r
```
| Question | Answer |
|---|---|
| Type of `u`? | **`int` first, then `str`** (after `chr`) → inconsistent type; a type checker flags it (`int | str`) |
| `u` negative? | **No if `b > 0`** (n>0 so `n % b` ≥ 0). If `b < 0`, Python's `%` yields ≤ 0 → yes |
| Always returns a value? | **Yes** – both paths return (`'0'` or `r`) |
| Divide by zero? | **Yes if `b == 0`** (`n % b`). Also `b == 1` → infinite loop (n never shrinks) |
| Minus sign in result? | **Only if `b < 0`** (negative `u` → `str(u)` contains `-`) |
Takeaway: static analysis answers with "depends on b" → needs a precondition `b >= 2`.

## 7. CI/CD & DevOps (L7)

**Automate everything feasible** (get code, dependencies, static analysis, compile, docs, tests, artifacts, ship, monitor). Anything not automatable → code review.

**Build system's 3 roles:** (1) define tasks (+ external resources) (2) define dependencies (a graph) (3) execute tasks.
**Good build:** dependency management, compile only what's needed, compile in correct order, removes tribal knowledge.

### Topological sort (build order) – how to solve
Dependencies form a **DAG**.
1. Compute **in-degree** (number of incoming edges) for each node.
2. Put all nodes with in-degree 0 in a queue.
3. Pop one, add to order, decrement in-degree of its neighbours; push any that reach 0.
4. Repeat. If not all nodes output → there's a **cycle**.

*Example:* Install deps → DB setup → Run app; Install deps → Tests; Static analysis (independent).
In-degrees: Install=0, Static=0, DB=1, Tests=1, Run=1 → order: `Install, Static, DB, Tests, Run` (Static can run in parallel).

**CI** = merge to mainline frequently (multiple times a day). Benefits: small change sets, early detection, easier integration, less debugging. *Don't break the build; use branches to keep main working.*
**CI pros:** problems from developer interaction found early; mainline = definitive system. **Cons:** long builds for large systems; dev platform ≠ target platform.

**DevOps pipeline stages**
| Stage | What |
|---|---|
| Continuous Integration | Merge frequently + continuous build (compile, dependencies, lint) + **sanity tests** |
| Continuous Delivery | Always-ready-to-deploy builds shipped to test/customers; deploy on demand |
| Continuous Testing | Automated tests, earliest feedback; entry = unit + integration pass |
| **Continuous Deployment** | Auto-deploy validated builds **to production**; mature teams |

*Delivery vs Deployment:* delivery = ready to release (often manual push); deployment = automatically released to production.

**DevOps** = culture + practices + tools to deliver faster & more reliably; extension of Agile (continuous delivery of working software).
**4 pillars:** **Collaboration** (theory of mind, equal participation, communication) · **Affinity** (relationship strength: shared values, culture, cohesion) · **Tools** · **Scaling**.

**DevSecOps** – security at every SDLC phase ("**shift left**"); motto *"software, safer, sooner."*
Benefits: find issues early, fix faster, shrink attack window, scale. Challenges: diverse technologies, **brittle pipelines**, hard to coordinate many security checks.

## 8. Testing Principles & Test Design (L8)

**Disney+ launch lesson:** tested streaming load but not account creation/login/browsing → *tested the wrong thing.*

### 7 Principles of Testing
1. **Testing shows presence, not absence, of defects** (Ariane 5, $370M).
2. **Exhaustive testing is impossible** → use heuristics.
3. **Start early** (cheapest to fix, least damage).
4. **Defects cluster** – ~10–20% of modules hold ~80% of bugs.
5. **Pesticide paradox** – same tests stop finding new bugs → vary tests.
6. **Context dependent** – pacemaker ≠ food app.
7. **Verification ≠ Validation** – *Verification: built it right (meets spec)?* *Validation: built the right thing (user needs)?*

**Ariane 5:** 64→16-bit conversion overflow reused from Ariane 4 assumptions; diagnostic data misread as flight data. Violated mostly principle **#1/#6/#7** (passed tests but context changed). Missing: **boundary/robustness tests** for larger velocity values, out-of-range conversion tests.

### Exhaustive testing calculation (Theme-park ride example)
Variables: age, date-time, ride time, public-holiday flag.
```
Test cases = ages × minutes/day × days in 5 years × ride-time values × holiday values
           = 116 × 1440 × 1826 × 120 × 2
```
Step by step: 116×1440 = 167,040 → ×1826 = 305,015,040 → ×120 = 36,601,804,800 → ×2 = **≈ 7.3 × 10¹⁰ (~73 billion)**.
*(Slide states ~72 billion; the "116" ages value doesn't match "int 2–17" which would be 16 values – just remember the method: **multiply the number of values of every input**. With 16 ages the total would be ≈ 10 billion – still impractical.)*

*Illustrative "zettaFLOP" calc (string tests):* if each char is one of 29 symbols (26 letters + `@ _ '`), strings of length up to n → about 29ⁿ tests. For n = 20: 29²⁰ ≈ 1.8×10²⁹. At 10²¹ tests/s → 1.8×10⁸ s ≈ **5.6 years**. (n isn't given on the slide; this shows the idea.)

### Specification-based (black-box) techniques
Advantages: no implementation bias, robust to code changes, no code familiarity needed, tests written before implementation.
Techniques: **equivalence partitioning, boundary value analysis, pairwise/combinatorial, random testing**, plus opportunistic/exploratory.

**Equivalence Partitioning – how to solve**
1. List inputs and spec rules.
2. Split each input into classes that behave the same (valid + invalid).
3. Pick **one** representative from each class.

*Example:* age 2–17 valid. Classes: `<2` (invalid), `2–17` (valid), `>17` (invalid), non-numeric (invalid) → test e.g. 1, 10, 18, "abc".

**Boundary Value Analysis – how to solve**
For range [min, max] test: **min−1 (invalid), min, min+1, nominal, max−1, max, max+1 (invalid)**.
*Example, age 2–17:* 1, 2, 3, 10, 16, 17, 18 → **7 tests**. (Standard BVA: 5 valid-side values; add min−1/max+1 for robustness.)

**Pairwise testing:** many bugs arise from interaction of 2 parameters; pairwise finds **~50–90% of defects**. Examples: 2-way (seniors × weekends), 3-way (+peak hours), 4-way.
*How to solve:* list parameters & values; build a table so that **every pair of values from any two parameters appears at least once** (tools: PICT, allpairs). *Count example:* 3 params × 2 values each = 8 exhaustive combos, pairwise needs only **4**.

### V-Model
Each development phase paired with a test level (requirements ↔ acceptance, design ↔ system, detailed design ↔ integration, coding ↔ unit).

### Test cases
Tells tester what to test, how, and expected result. Be short in title, strong description, concise, include expected result, reusable.
**Types:** Positive (valid login works) · Negative (invalid login blocked) · **Destructive** (how far before it breaks).
**Test suite** = container of tests; states **Active / In-Progress / Completed**; can hold functional & non-functional tests; a case may be in several suites.
**Software reliability** = probability of failure-free operation for a specified time in a specified environment.

## 9. Inspection & Development Testing (L9)

| | Inspection (static verification) | Testing (dynamic verification) |
|---|---|---|
| What | People examine source/representation | Execute with test data |
| When | Before implementation, any artifact | Needs runnable code |

**Inspection advantages:** errors can't mask each other; incomplete systems can be inspected without harnesses; also checks standards, portability, maintainability.

**Stages of testing:** development testing (by dev team) → release testing (separate team) → user testing.

**Development testing**
| Level | Focus |
|---|---|
| **Unit** | Individual functions/methods/classes tested **in isolation** (defect testing) |
| **Component** | **Component interfaces** (integrated units) |
| **System** | **Component interactions**, emergent behaviour |

**Object class testing:** test all operations, set/query all attributes, exercise all states; inheritance makes it harder.
**Automated unit tests:** use frameworks like **JUnit**; extend generic test classes.
**Interface types:** parameter · shared memory · procedural · message passing.
**Interface errors:** *misuse* (wrong param order) · *misunderstanding* (wrong assumptions) · *timing* (stale data).
**Interface test guidelines:** extremes of ranges · **null pointers** · force failures · stress test message passing · vary activation order in shared memory.
**Regression testing:** rerun all tests after every change; must pass before commit; cheap if automated.

## 10. Release, User, Performance Testing & Chaos Engineering (L10)

**Release testing** – black-box, from spec, by a **separate team**. Goal: show system is good enough for external use (**validation testing**). Dev-team system testing = **defect testing**.

**User testing** – essential since user environment affects reliability/performance/usability and can't be replicated.
| Type | Who/where |
|---|---|
| **Alpha** | Users work with dev team **at developer's site** |
| **Beta** | Release to users to find problems **in their environment** |
| **Acceptance** | Customer decides to accept system (custom systems) |
*Agile:* embedded customer defines tests, no separate acceptance phase (issue: is the user "typical"?).

**Performance testing:** performance bugs = bad performance on some inputs, degradation over time, differences across versions/platforms. Hard: threshold unclear, noisy measurements, hard diagnosis; no crash or wrong output. Use **performance regression tests** (log & compare times), **profiling** (measure time/memory) and **tracing** (sequence of calls).
**Soak testing:** heavy load over a long period (finds memory leaks).

**Chaos engineering:** experiment on a live system to build confidence it withstands turbulence – deliberately kill components and watch failover.
- **Google:** Sao Paulo network shutdown exposed hidden dependency in Mexico; data-centre restart ran out of DHCP leases.
- **Netflix:** Chaos Monkey kills AWS instances/network/configs; key metric **Stream Starts per Second (SPS)** = availability.
- Microservice failure modes: partitions, instance down, delays, overload, out of memory/CPU.

## 11. Static vs Dynamic Testing & Cyclomatic Complexity (L11)

**Static testing = Verification** (no execution): document reviews, walkthroughs, inspections, feasibility analysis, code review.
**Static analysis** covers: code quality, data flow, control flow, **cyclomatic complexity**.
**Dynamic testing = Validation:** run the system, give input, compare with expected. Pros: finds complex defects. Cons: time & budget.

### Cyclomatic Complexity (CC) – measures number of **linearly independent paths**
**Formula:** `M = E − N + 2P`  (E = edges, N = nodes, P = connected components; for a single program/function **P = 1**, so `M = E − N + 2`)

**Shortcuts (all give same answer):**
1. `M = number of decision points (if, while, for, case, &&, ||) + 1`
2. `M = number of regions in the planar CFG` (including the outside region)
3. `M = E − N + 2`

**How to solve step-by-step**
1. Break code into **basic blocks** (straight-line statements) → nodes. Add Entry/Exit if needed.
2. Draw directed edges for each possible jump (if → two edges, loop → back edge + exit edge).
3. Count E and N → apply formula.
4. **Verify** with decision-count + 1.

**Worked examples from slides**
| Example | E | N | M = E−N+2 | Decision check |
|---|---|---|---|---|
| Figure with 7 nodes, 7 edges | 7 | 7 | **2** | 1 decision + 1 |
| Insertion-sort-like (`for`, `for`, `while`) | 16 | 14 | **4** | 3 decisions + 1 = 4 ✓ |
| Power function (`if y<0`, `while`, `if y<0`) | 16 | 14 | **4** | 3 decisions + 1 = 4 ✓ |
| Nested while/while/if (selection-sort-like), n=4 | 9 | 7 | **4** | 3 decisions + 1 = 4 ✓ |

**Interpretation:** M also = minimum number of test cases needed for **basis-path coverage**.
**Disadvantages:** measures control complexity not data complexity; nested conditions harder than flat but same score; misleading for simple comparisons/decisions.

### Dynamic testing – code-based
- **Control-flow criteria:** statement, **branch** (every branch taken at least once), condition coverage.
- **Data-flow criteria:** paths through variable definitions & uses.
- *Coverage definitions:* Statement coverage = executed statements / total statements × 100. Branch coverage = executed branches / total branches × 100. *E.g. 8 of 10 statements executed → 80%.*

### Dynamic testing – fault-based
| Technique | Idea |
|---|---|
| **Error guessing** | Use experience/intuition about plausible faults |
| **Fault seeding** | Deliberately inject faults (secretly) to measure test effectiveness |
| **Mutation testing** | Change single statements (mutants); a good test suite should **kill** (fail) all mutants |

*Mutation score calc:* `killed mutants / total non-equivalent mutants × 100`. E.g. 18 killed of 20 → 90%.
*Fault seeding estimate:* if you seed 20 faults and testers find 15 seeded + 30 real faults → est. total real faults ≈ 30 × (20/15) = **40**.

**Based on approach:** Equivalence partitioning + BVA · Specification-based · Intuition-based · Usage-based · Application-domain.

## 12. Software Configuration Management (L12-14)

**Scenario:** 2 AM merge of Alice (bug fix) + Bob (payments) + Charlie (UI) → system crashes and no one knows which version worked → *this is what SCM prevents.*

**SCM** = discipline to **identify, track, control and audit changes** to code, documents and other items. Goals: planned coordination, avoid config problems, manage concurrent updates, build management, defect tracking.

**Why:** multiple concurrent developers, multiple versions, released systems, changing requirements, custom configurations, multi-platform, cost control.

**4 basic elements**
| Element | Purpose |
|---|---|
| **Configuration item identification** | Define baseline components |
| **Configuration control** | Initiate/evaluate/approve or reject changes |
| **Configuration auditing** | Check current state vs baseline |
| **Status accounting** | Record how the system evolved |

**Benefits:** orderly development & release, only approved changes, matches specs, accurate documentation, impact assessment, prevents unauthorised change.
**Google:** monorepo ~2 billion LOC, 40,000+ commits/day, test on every commit, instant rollback, full audit trail.

**Roles:** **Configuration Manager** (identify CIs, define procedures) · **Developer** (check-in, resolve conflicts) · **Auditor** (validate promotion/release process) · **Change Control Board (CCB) member** (approve/reject changes).
**SCM Plan:** CIs & naming, responsibilities, change/version policies, tools, CM database.

**Activities:** CI identification · directories · baselining · branch mgmt · version mgmt · build · install · promotion · change · release · defect mgmt.

**Configuration item:** anything under version control – code, test drivers, requirements/design docs, manuals, system configs. *Too early = bureaucracy; too late = chaos.*

**Baseline:** formally reviewed and agreed; changes only via formal review. (e.g. Baseline A = APIs defined, empty bodies; Baseline B = data access implemented & tested.)

**Branching:** copy/clone of code for concurrent development, multiple versions, experimentation; merge frequently to reduce conflicts. Strategies: single, by customer, by developer, by module.
| Strategy | Best for | Features |
|---|---|---|
| **GitFlow** | Large product (~50 devs), strict releases, multiple prod versions | `main`, `develop`, `feature/`, `release/`, `hotfix/` |
| **Trunk-based** | Small team (~4), rapid iteration, weekly releases | Single main, short-lived branches, frequent integration, **feature flags** |

### Version numbering – how to solve (`MAJOR.MINOR.PATCH`, e.g. 7.5.4)
| Change | Bump | Example |
|---|---|---|
| Breaking / major redesign | **MAJOR** (reset minor, patch to 0) | v1.1.0 → **v2.0.0** UI redesign |
| New backward-compatible feature | **MINOR** (reset patch) | v1.0.1 → **v1.1.0** payment added |
| Bug fix | **PATCH** | v1.0.0 → **v1.0.1** registration fix |

**Version vs Release vs Revision:** *Version* = distinct functionality; *Release* = formal distribution of an approved version; *Revision* = fix that doesn't change documented functionality.

**Build management:** tools Make, Ant, Maven; build process = fetch → compile & check deps → link → test & artifacts → archive logs & notify (may bump version). Skips recompiling unchanged files.
**Install management:** first customer interaction; failure = bad perception; tools: zip, shell scripts, InstallShield, InstallAware, Jenkins.
**Promotion management:** move from private workspace to central master using promotion policy (baseline criteria + verification). *Food for thought:* code with only warnings can be promoted if policy allows – but strict policies treat warnings as errors.
**Change policies:** informal (research) vs formal (external items & releases); controlled at **promotion** and **release** points.

**Defect management process:** Discover → Report (Jira/Bugzilla) → Validate (reproduce) → Analyze (severity: Critical/High/Medium/Low) → Assign → Fix → Verify → Close → Release.
*Bug* = consequence of a coding fault; *Defect* = deviation from requirements.

**SCM tool types:** source code admin (RCS, CVS, ClearCase, GitHub) · build (Make, CruiseControl, FinalBuilder, Maven) · installation (InstallShield, DeployMaster, InstallAware, WiseInstaller) · bug tracking (Bugzilla, FogBugz, Trac, Backlog).

**SCM in Agile/Scrum:** whole-team responsibility, automated. Flow: pull latest → feature branch → change locally → run tests → commit/push → CI runs → pull-request review → merge to main → auto-deploy to staging.

### Change management
Ensures system evolution is managed; prioritises urgent & cost-effective changes. Process: request → analysis (costs/benefits) → CCB decision → implement → QA → CM.
**Change request form fields:** project, number, requester/date, requested change, analyzer/date, components affected/associated, assessment, **priority**, estimated effort, CCB decision date & decision, implementor, QA/CM dates.
**Factors in change analysis:** consequences of not changing · benefits · number of users affected · cost · release cycle.
**Agile:** customers directly involved in prioritising changes; **refactoring is a normal part of development**, not overhead.

### SBOM (Software Bill of Materials)
Inventory of all components/libraries (open-source + proprietary) – a "parts list" for software. Contents: package name, version, origin, checksum, license, relationships.
**Why:** *Security* – quickly check if affected by vulnerabilities (e.g. **Log4Shell**), find transitive dependencies · *Compliance* – licences (GPL/MIT/Apache) · *Traceability/audit* – "which version of libxyz?".
**Standards:** **SPDX** (Linux Foundation) · **CycloneDX** (OWASP, security-focused) · **SWID** (ISO, enterprise asset mgmt).
**Tools:** Syft (`syft myapp:latest -o cyclonedx-json`) · Trivy · OWASP Dependency-Check · GitHub Actions auto-SBOM.
*Example entry:* log4j-core **2.14.1** (`pkg:maven/...`, Apache-2.0) → that exact version is the Log4Shell-vulnerable one, which is why an SBOM helps.

## 13. Formula & Quick-Solve Cheat Sheet

| Topic | Formula / procedure |
|---|---|
| **Cyclomatic complexity** | `M = E − N + 2P` (P=1 normally) = decisions + 1 = regions |
| **Exhaustive test count** | Multiply number of values for every input |
| **BVA (one variable, range [min,max])** | min−1, min, min+1, nominal, max−1, max, max+1 |
| **Equivalence partitioning** | One test per valid & invalid class |
| **Pairwise** | Every pair of values from every two params appears at least once |
| **Topological sort** | In-degree 0 first → remove → repeat; leftover nodes ⇒ cycle |
| **Statement coverage** | executed statements ÷ total × 100 |
| **Branch coverage** | executed branches ÷ total × 100 |
| **Mutation score** | killed mutants ÷ total (non-equivalent) mutants × 100 |
| **Fault seeding estimate** | real faults found × (seeded total ÷ seeded found) |
| **Sprints needed** | backlog points ÷ velocity |
| **Defect reduction %** | (before − after) ÷ before × 100 (4.5→0.82 ≈ 82%) |
| **Semantic versioning** | breaking→MAJOR, feature→MINOR, fix→PATCH |
| **Dangling else** | else pairs with nearest unmatched if |

### Frequently confused pairs
- **Verification** (right way, spec) vs **Validation** (right product, user needs)
- **Static** (no execution, false positives) vs **Dynamic** (execution, false negatives)
- **Continuous Delivery** (ready to release) vs **Continuous Deployment** (auto to production)
- **Alpha** (dev site) vs **Beta** (user site) vs **Acceptance** (customer sign-off)
- **System testing** (dev team, find defects) vs **Release testing** (separate team, validate)
- **Unit** (isolation) vs **Component** (interfaces) vs **System** (interactions)
- **Version / Release / Revision**
- **Linter / pattern bug finder / type checker / data-flow analysis** (shallow → deep, cheap → costly)
- **Coding standard** (enforced rules) vs **guideline** (generic suggestions)
- **Stub** (fake called function) vs **harness/driver** (calls the module under test)
